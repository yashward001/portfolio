### Two bad options, so I built a third

Desktop automation usually means record-and-replay tools that break on any UI change, or scripting APIs that need a developer for every new workflow. Neither understands plain language, neither recovers from failure, and neither shows you what ran and why.

ATLAS is five parts in one loop: voice in, a plan from Gemini, a human gate, Playwright doing the clicking, and a live feed back to the UI.

</AtlasBeat>

<AtlasBeat scene="voice">

### You speak, and the audio goes straight to Gemini

The **Gemini Live API** streams microphone audio directly for transcription and intent extraction. There’s no separate speech-to-text step in between, so planning starts sooner.

Voice or text, the request has to end up as typed, pre-approved UI actions. No ad-hoc scripting.

</AtlasBeat>

<AtlasBeat scene="plan">

### The registry is the model’s entire vocabulary

Every automatable UI action is a **Firestore** document with its selector, typed parameters, pre- and postconditions, risk level, confidence score and auto-heal history.

**Gemini 2.5 Flash** receives the whole registry as tools and returns an ordered list of capability IDs with parameters filled in. It can *choose* actions, but it can’t write Playwright code, so everything that can run was declared in advance.

Because UI knowledge lives in the registry and not the prompt, a selector can change without touching the inference layer or redeploying.

</AtlasBeat>

<AtlasBeat scene="approve">

### Risky plans stop at the gate

Risk level belongs to each capability and is set when it’s authored. The model never decides at runtime whether a step needs a human.

Here, the step that posts to a team channel needs sign-off, so the whole plan waits for an explicit approval before anything runs.

</AtlasBeat>

<AtlasBeat scene="execute">

### Playwright clicks, and keeps the receipts

Each capability ID resolves against the registry to a typed action: click, fill, navigate or assert. Steps run in order, and each one saves a screenshot with its target’s bounding box highlighted.

When a step can’t find its target in time, retry logic takes over instead of failing the run.

</AtlasBeat>

<AtlasBeat scene="stream">

### Every update is pushed live to the UI

A **WebSocket** bridge streams each step’s status (pending, running, success, failed, retrying) along with the annotated screenshots and approval prompts.

The frontend is a formal state machine, 11 states and 9 events, so every phase is an explicit node rather than a flag buried in a component. Framer Motion animates each transition, and the finished run leaves a full transcript to audit.

</AtlasBeat>

## What I’d do next

- **Capability discovery:** crawl an app’s UI and propose new capability records instead of writing them by hand.
- **Drift detection:** replay recorded execution traces against UI updates to catch selectors that have gone stale.
- **Approval routing:** let teams decide who approves what, based on a capability’s risk level, instead of a single yes/no gate.
